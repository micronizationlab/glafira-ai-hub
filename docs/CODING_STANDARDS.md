# Стандарты разработки GLAFIRA

## 1. Поддерживаемые инструменты

Версии сверяются с Gradle Version Catalog и фактическими workflow; этот документ не заменяет конфигурацию сборки.

- Android: Kotlin **2.0.21**, JVM target **17**, Android Gradle Plugin **8.7.2**, Gradle Wrapper **8.9**.
- Windows: .NET **8**; язык C# — версия, заданная проектом/SDK.
- iOS: Swift — версия, поддерживаемая текущим Xcode и CI.
- Не обновляйте версии платформы или toolchain в рамках несвязанного PR.

## 2. Архитектура и безопасность

- Соблюдайте актуальные контракты Core, владения задачами, fencing, ACK/outbox и failover.
- Deny by default; минимальные полномочия по владельцу, проекту, задаче, устройству, capability и сроку действия.
- Не помещайте секреты, токены, пароли, приватные ключи или персональные данные в исходный код, fixtures, логи, скриншоты и PR.
- CI-секреты храните в GitHub Actions Secrets; локальные значения — в local.properties (он должен оставаться вне Git).
- Runtime-секреты храните через Android Keystore, Windows DPAPI/защищённое хранилище или соответствующий системный механизм.
- Криптографию реализуйте через проверенные платформенные API/библиотеки; не создавайте собственные алгоритмы.
- Не выполняйте внешние, финансовые, публикующие или разрушительные действия без предусмотренного разрешения владельца.
- Любая работа с пользовательскими ресурсами должна быть прозрачной, ограниченной и отзывной.

## 3. Тестирование

- Добавляйте unit-тесты для новой логики и регрессионные тесты для исправлений.
- Для межмодульных контрактов добавляйте integration/conformance-тесты.
- Критичные пользовательские сценарии подтверждайте acceptance/instrumentation-тестами на поддерживаемой среде.
- Указывайте фактическое число выполненных тестов и прикладывайте отчёты CI.
- Skipped, cancelled, queued и отсутствующие тесты не являются успешным результатом.
- Цель покрытия нового кода — 80% там, где измерение применимо; это целевой показатель, а не блокирующий порог до появления согласованного измерителя и baseline.

## 4. Коммиты и PR

Используйте Conventional Commits, например:
- feat(core): add durable task lease
- fix(android): restore project selector
- docs(ci): clarify exact-head validation
- test(bridge): cover reconnect recovery
- refactor(core): isolate repository boundary
- chore(ci): pin validation tooling

Один PR — одна независимо проверяемая задача. Ориентир размера — не более 400 изменённых строк; большие изменения разбиваются на зависимые PR. Укажите зависимости, риски, тесты и план отката. Self-review обязателен.

## 5. Ревью и интеграция

- Проверяйте полный diff и точный HEAD PR, а не только описание.
- Не объединяйте устаревшую ветку без обновления и повторной проверки.
- Не обходите branch protection и не считайте mergeability заменой ревью.
- После merge проверяйте новый SHA main и post-merge CI.
- Владелец проекта сохраняет право архитектурного решения; предложения помощников не являются утверждёнными решениями.
