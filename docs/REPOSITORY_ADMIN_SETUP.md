# Настройки репозитория и процесса разработки

Этот документ — инструкция для владельца. Он не утверждает, что настройки GitHub уже включены.

## Защита main

Откройте Settings → Branches и создайте правило для main (или эквивалентный ruleset):

- Требовать Pull Request перед слиянием.
- Требовать минимум одно одобрение независимого ревьюера.
- Сбрасывать устаревшие approvals после новых коммитов.
- Требовать актуальную относительно main ветку.
- Запретить force-push и удаление main.
- Применять правила также к администраторам, если владелец согласен с тем, что аварийное слияние без независимого reviewer будет невозможно.
- Не разрешать обход правил через bypass list без отдельного решения владельца.
- Включить требование Code Owner review для защищаемых путей после проверки, что CODEOWNERS корректно распознаётся GitHub.

Файл [CODEOWNERS](../.github/CODEOWNERS) назначает владельца репозитория ответственным reviewer по умолчанию. Само наличие CODEOWNERS не включает обязательное одобрение: это отдельный параметр branch protection/ruleset.

## Required status checks

Сначала дождитесь успешных проверок на PR, затем выбирайте фактические имена check contexts из GitHub UI. В текущей конфигурации используются job names:

- Exact-head CI summary — итог change-aware workflow.
- Verified secrets scan — TruffleHog job.
- Workflow lint — при изменениях workflow.
- Android JVM tests, Android debug APK contracts и SharedAndroid emulator acceptance contracts — когда выбраны детектором изменений.
- Shared contracts, Windows Agent, Windows Desktop Hub и iOS — для соответствующих изменений.

Не копируйте старые названия вида CI / lint или Android Emulator Tests / emulator: они не совпадают с текущим workflow. Change-aware проверки могут быть skipped для нерелевантных файлов; skipped не означает, что тесты были выполнены. Итоговый Exact-head CI summary должен завершиться success.

## Подпись коммитов и 2FA

- Require signed commits можно включить после проверки, что все активные участники умеют подписывать коммиты и ключи восстановления доступны владельцу.
- Владелец и все участники должны включить 2FA в настройках своих GitHub-аккаунтов.
- Organization-wide enforcement доступен только для GitHub Organization. На момент подготовки этого документа micronizationlab отображается как личный аккаунт, поэтому путь Organization Settings → Member privileges здесь неприменим.

## Коллабораторы и доступ

Добавляйте участников постепенно через Settings → Collaborators. Начните с тех, кому действительно назначены задачи. Выдавайте минимально достаточный уровень доступа; административные права не нужны для обычной разработки. Перед приглашением проверьте личность участника и согласуйте область ответственности. Удаляйте доступ при завершении сотрудничества и периодически пересматривайте список.

Не добавляйте вымышленных участников и не назначайте роли без согласия владельца. CODEOWNERS задаёт reviewer-маршрутизацию, но не заменяет контроль доступа.

## GitHub Projects

Создайте доску проекта вручную в GitHub Projects и свяжите её с репозиторием. Предлагаемые статусы:

1. Backlog
2. Ready for Sprint
3. In Progress
4. In Review
5. Testing
6. Done

Рекомендуемые поля:
- Priority: используйте действующую шкалу проекта P0–P5 из IMPLEMENTATION_ROADMAP.md; не заменяйте её новой шкалой P0–P3.
- Module: Core, Android, Desktop, Bridge/Agent, Backup, CI/Security, Docs.
- Estimate: часы или story points (один формат на доске).
- Assignee: ответственный участник.
- Milestone: релиз или спринт.

Двухнедельный спринт и WIP до двух задач на участника — предлагаемый режим планирования, а не изменение утверждённой очереди 11 направлений. Срочные P0/P1 блокеры могут требовать отдельной обработки. Done ставится только после критериев приёмки и проверки.

## Еженедельная отчётность

Отчёт должен показывать:
- завершённые и реально влитые PR;
- текущий main SHA и post-merge CI;
- PR в работе, на ревью и заблокированные;
- выполненные тесты, skipped проверки и найденные дефекты;
- блокеры, владельцев и следующий конкретный шаг.

Не публикуйте секреты, персональные данные и внутренние логи с чувствительными значениями.
