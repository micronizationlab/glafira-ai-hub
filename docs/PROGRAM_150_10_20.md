## Meaning

- **150** — the baseline 150-step engineering program.
- **10** — ten parallel workstreams. Work may proceed concurrently where dependencies and file ownership do not conflict.
- **20** — twenty sequential improvement cycles. Each cycle is planned from verified outcomes and remaining risks of the previous cycle; no cycle is marked complete by documentation alone.

The 20 cycles are not a claim that 3,000 tasks already exist or are complete. The baseline 150 steps remain the canonical initial backlog. The current repository ledger also contains 50 supplementary expansion steps numbered 151–200; these are tracked separately and must not silently change the 150-step baseline denominator. Cycle 1 executes and validates the baseline while using supplementary items as additional evidence-driven work; later cycles are derived from real test results, device acceptance, operational evidence and owner-approved product requirements.

## Operating rules

1. Keep ten workstreams active. If one waits for CI, credentials, hardware, review or owner input, advance independent work in other streams.
2. Never bypass branch protection, required review, exact-head CI or release acceptance.
3. Distinguish implemented, partially implemented, blocked, awaiting CI, skipped and physically accepted. Skipped checks are not passes.
4. A design document, issue, PR, or green unit test alone does not prove end-to-end completion.
5. Keep provider choice independent from authorization. Yandex Cloud/API is a permitted provider option; an unimplemented adapter is a delivery gap, not a global prohibition. No provider is mandatory.
6. Keep Android Core and Windows Desktop Core independently useful. A Windows Hub outage must not disable supported Android-local work, and an Android outage must not disable supported Desktop-local work.
7. Default unverified Windows Agent handlers to DRY_RUN. Allow owner-configured LIVE only for explicitly allowlisted, tested operation types and risk scopes; external side effects remain approval-gated.
8. Owner generation must fence every ownership-sensitive task, approval, grant, lease, result and recovery mutation.
9. Preserve durable task queues and recoverable configuration. Corruption or missing runtime preferences must not silently discard tasks or permissions.
10. Keep financial execution disabled until ownership fencing, approvals, bank integration security and exact owner confirmation pass acceptance.

## Twenty-cycle lifecycle

1. **Cycle 1 — Baseline closure:** execute the canonical 150-step backlog, close inherited audit decisions and prove the current architecture.
2. **Cycle 2 — Security hardening:** close ownership, approvals, grants, revocation, key rotation and stale-generation attack paths.
3. **Cycle 3 — Recovery reliability:** crash matrix, portable backups, clean-install restore and verified recovery.
4. **Cycle 4 — Provider parity:** provider registry, Yandex Cloud/API adapter proof, quotas, health checks and failover policy.
5. **Cycle 5 — Android autonomy:** durable runtime configuration, local task continuity, backup scheduling and degraded operation.
6. **Cycle 6 — Android Bridge:** pairing, authentication, scoped commands, revocation and device acceptance.
7. **Cycle 7 — Desktop Core:** installable Desktop runtime, canonical queue and owner policy.
8. **Cycle 8 — Windows Hub:** Core admission adapter, payload handling, durable result reconciliation.
9. **Cycle 9 — Windows Agent:** typed handlers, lease recovery, constrained LIVE execution and two-PC testing.
10. **Cycle 10 — Dual-Core continuity:** reconnect, handoff, generation fencing, partitions and no split-brain acceptance.
11. **Cycle 11 — Identity portability:** Supabase export/restore, provider migration proof and account recovery.
12. **Cycle 12 — Tool and connector broker:** scoped OAuth/API integrations, credential isolation and audit.
13. **Cycle 13 — User experience:** reliable approvals, task status, voice and accessible UI contracts.
14. **Cycle 14 — Observability:** diagnostics, redacted traces, queue health, cost and provider telemetry.
15. **Cycle 15 — Performance and concurrency:** SQLite/WAL contention, load, queue fairness and bounded parallelism.
16. **Cycle 16 — Privacy and data boundaries:** project isolation, provider data classifications, retention and deletion.
17. **Cycle 17 — Business workflows:** CRM, commerce, communications and document automation with owner policies.
18. **Cycle 18 — Financial readiness:** read-only banking, reconciliation and workpapers; execution remains separately gated.
19. **Cycle 19 — Release and resilience:** upgrade/rollback, disaster recovery, security review and multi-device acceptance.
20. **Cycle 20 — Production certification:** full regression, operational runbooks, owner acceptance and release decision.

Cycle descriptions are planning horizons, not completion claims. Each cycle receives its own entry criteria, measurable tests, exit criteria and evidence links before it starts.
